== PROJECT: MediCoreRx (personal project) ==
Page on the site: https://adhikchintalwar.github.io/adhik-portfolio/#/project/medicorerx
Source code link: not listed on the page yet (suggest contacting Adhik if someone asks for it).
What it is: MediCoreRx is a personal project Adhik built (it is not work he did at an employer). It is a multi-tenant SaaS platform for pharmaceutical wholesale and retail ordering, written as a full-stack TypeScript monorepo (React, Node.js and Express, SQL Server). The code base is called DeviMedical (monorepo version 0.2.0).
The idea: wholesalers run inventory, billing and compliance in an admin ERP; pharmacies order online through a separate portal; a platform team approves accounts and supports the tenants.
The problem it addresses (Indian pharmaceutical distribution): wholesalers and distributors must track stock by batch and expiry, GST, drug licences, customers and field representatives; retail pharmacies want to order digitally instead of by phone; a platform operator needs to onboard organisations, verify licences and give support without sharing one password across all tenants. Small distributors often work from spreadsheets or legacy desktop ERP, and this project replaces that with a modern web stack.
Four web apps, two Express APIs, one shared TypeScript package and one SQL Server database:
- Admin app (wholesaler staff), a web ERP called "Proficenter".
- Ordering app (pharmacy buyers), a B2B ordering portal.
- Platform app (the MediCoreRx operations team): approvals, support access, health.
- Marketing site (public), a static landing page.
Why two APIs: the admin API is large (sales, purchases, batches, parties, reports, platform routes, representative sessions). The ordering API is smaller and CORS-locked to the ordering domains only, which reduces the impact of a customer-facing bug and keeps customer sessions separate from admin sessions. Both APIs use the same SQL database; multi-tenancy comes from an organisation_id on rows, not from a separate database per customer.
Admin ERP features: dashboard, masters setup (representatives, areas, taxes, registration types), customers and vendors (GSTIN, drug licence numbers, credit, schemes), catalog and catalog import, product batch master, receiving customer orders, sales and purchases with GST, batches and FIFO stock, purchase import, returns (customer sale returns and vendor purchase notes), receipts, payments and vouchers, night audit, stock adjustments, alerts and reports. Domain logic includes FIFO batch consumption, a stock ledger, customer schemes such as free-quantity rules, drug licence validity warnings, and organisation codes so pharmacies link to the right wholesaler. Field representatives can use a separate PIN session so they do not share the owner's password.
Ordering portal: pharmacies sign up with phone OTP, give representative and pharmacy details and their drug licence number, state and validity, may wait for platform approval, link a wholesaler with an organisation code, browse products, fill a cart and place orders, then track orders, pending receipts and receipt history, re-order and see outstanding totals. Orders placed there appear in the admin app under Receive orders, and accepting an order deducts stock through the same inventory engine as a manual sale, so there is one source of truth.
Platform portal: for the MediCoreRx team only. Overview counts, approvals (business accounts for wholesaler sign-ups and customer accounts for ordering sign-ups), organisations (with suspension and a reason), billing, inbox, announcements, compliance, health, and time-boxed support access sessions that are logged for audit.
Security: Firebase Authentication (phone, email and Google) for identity; JWT sessions with separate secrets for the admin and ordering APIs; every API call resolves the organisation from the signed-in user; platform routes need a platform-owner check plus an optional IP allowlist; the legacy username and password admin login is disabled in production; representative PIN sessions use their own header.
Compliance and trust features: a licence responsibility clause on admin and ordering signup, a platform disclaimer on sign-in screens, drug licence fields with validity status in the UI, approval workflows, and GSTIN, jurisdiction and drug licences captured at organisation signup.
Data: SQL Server with schema migrations that run on startup in both APIs, plus a large medicine reference library (hundreds of thousands of reference rows) kept separate from each organisation's catalog.
Delivery: locally it runs with npm scripts or Docker Compose (SQL Server, both APIs and both SPAs). In production it was set up with the front ends on Firebase Hosting, the APIs as containers on Azure App Service (from Azure Container Registry), Azure SQL, custom domains, and a GitHub Actions workflow that builds and pushes the API images on every push to main.
Status: Adhik later shut the Azure environment down to stop cloud spend, so there is no public live demo. The stack still runs locally and with Docker.
Stack: React 18, React Router, Vite, TypeScript (strict), Node 20, Express, the mssql driver, Firebase Auth and Hosting, Azure, Docker, GitHub Actions, npm workspaces, ESLint.
Problems he solved: (1) the order flow end to end, so pharmacies can order without calling and wholesalers receive the orders with stock handled in one place; (2) a confusing case where one phone number could create both an empty customer record and a full wholesaler record, fixed by separating the two account types in the approvals screens and removing orphan customer records; (3) an admin signup that failed with a browser CORS error, which turned out to be the API being down (Azure returned 503 because the free-tier SQL database had paused), so he fixed the database billing mode, improved client-IP detection behind the proxy and restarted the apps.
