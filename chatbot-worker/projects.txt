== PROJECT: MediCoreRx (personal project) ==
Page on the site: https://adhikchintalwar.github.io/adhik-portfolio/#/project/medicorerx
Source code link: not listed on the page yet (suggest contacting Adhik if someone asks for it).
What it is: MediCoreRx is a personal project Adhik built (it is not work he did at an employer). It is a multi-tenant SaaS platform for pharmaceutical wholesale and retail ordering, written as a full-stack TypeScript monorepo (React, Node.js and Express, SQL Server). The code base is called DeviMedical (monorepo version 0.2.0).
The idea: wholesalers run inventory, billing and compliance in an admin ERP; pharmacies order online through a separate portal; a platform team approves accounts and supports the tenants.
The problem it addresses (Indian pharmaceutical distribution): wholesalers and distributors must track stock by batch and expiry, GST, drug licences, customers and field representatives; retail pharmacies want to order digitally instead of by phone; a platform operator needs to onboard organisations, verify licences and give support without sharing one password across all tenants. Small distributors often work from spreadsheets or legacy desktop ERP, and this project replaces that with a modern web stack.
Four web apps, two Express APIs, one shared TypeScript package and one SQL Server database:
- Admin app (wholesaler staff), a web ERP called "Proficenter".
- Ordering app (pharmacy buyers), a B2B ordering portal.
- Platform app (the MediCoreRx operations team): approvals, support access, health.
- Marketing site (public), a static landing page.
Why two APIs: the admin API is large (sales, purchases, batches, parties, reports, platform routes, representative sessions). The ordering API is smaller and CORS-locked to the ordering domains only, which reduces the impact of a customer-facing bug and keeps customer sessions separate from admin sessions. Both APIs use the same SQL database; multi-tenancy comes from an organisation_id on rows, not from a separate database per customer.
Admin ERP features: dashboard, masters setup (representatives, areas, taxes, registration types), customers and vendors (GSTIN, drug licence numbers, credit, schemes), catalog and catalog import, product batch master, receiving customer orders, sales and purchases with GST, batches and FIFO stock, purchase import, returns (customer sale returns and vendor purchase notes), receipts, payments and vouchers, night audit, stock adjustments, alerts and reports. Domain logic includes FIFO batch consumption, a stock ledger, customer schemes such as free-quantity rules, drug licence validity warnings, and organisation codes so pharmacies link to the right wholesaler. Field representatives can use a separate PIN session so they do not share the owner's password.
Ordering portal: pharmacies sign up with phone OTP, give representative and pharmacy details and their drug licence number, state and validity, may wait for platform approval, link a wholesaler with an organisation code, browse products, fill a cart and place orders, then track orders, pending receipts and receipt history, re-order and see outstanding totals. Orders placed there appear in the admin app under Receive orders, and accepting an order deducts stock through the same inventory engine as a manual sale, so there is one source of truth.
Platform portal: for the MediCoreRx team only. Overview counts, approvals (business accounts for wholesaler sign-ups and customer accounts for ordering sign-ups), organisations (with suspension and a reason), billing, inbox, announcements, compliance, health, and time-boxed support access sessions that are logged for audit.
Security: Firebase Authentication (phone, email and Google) for identity; JWT sessions with separate secrets for the admin and ordering APIs; every API call resolves the organisation from the signed-in user; platform routes need a platform-owner check plus an optional IP allowlist; the legacy username and password admin login is disabled in production; representative PIN sessions use their own header.
Compliance and trust features: a licence responsibility clause on admin and ordering signup, a platform disclaimer on sign-in screens, drug licence fields with validity status in the UI, approval workflows, and GSTIN, jurisdiction and drug licences captured at organisation signup.
Data: SQL Server with schema migrations that run on startup in both APIs, plus a large medicine reference library (hundreds of thousands of reference rows) kept separate from each organisation's catalog.
Delivery: locally it runs with npm scripts or Docker Compose (SQL Server, both APIs and both SPAs). In production it was set up with the front ends on Firebase Hosting, the APIs as containers on Azure App Service (from Azure Container Registry), Azure SQL, custom domains, and a GitHub Actions workflow that builds and pushes the API images on every push to main.
Status: Adhik later shut the Azure environment down to stop cloud spend, so there is no public live demo. The stack still runs locally and with Docker.
Stack: React 18, React Router, Vite, TypeScript (strict), Node 20, Express, the mssql driver, Firebase Auth and Hosting, Azure, Docker, GitHub Actions, npm workspaces, ESLint.
Problems he solved: (1) the order flow end to end, so pharmacies can order without calling and wholesalers receive the orders with stock handled in one place; (2) a confusing case where one phone number could create both an empty customer record and a full wholesaler record, fixed by separating the two account types in the approvals screens and removing orphan customer records; (3) an admin signup that failed with a browser CORS error, which turned out to be the API being down (Azure returned 503 because the free-tier SQL database had paused), so he fixed the database billing mode, improved client-IP detection behind the proxy and restarted the apps.

== PROJECT: Baby Equity Research (personal project; one of two separate projects Adhik calls Baby) ==
Page on the site: https://adhikchintalwar.github.io/adhik-portfolio/#/project/baby-research
Source code link: not listed on the page yet (suggest contacting Adhik if someone asks for it). Both Baby projects live in one repository.
Naming: Adhik has two separate projects called Baby: this equity research platform and the Baby Voice Assistant. If a visitor only says "Baby", mention both briefly and ask which one they mean.
What it is: a research system that scans the market, builds an evidence file on a stock, scores that evidence with deterministic code, watches the setup and lets a person approve a simulated paper trade. The language model can explain the research file, but it cannot change the score, override risk or send an order. It is a research tool, not an autonomous trader. Real-money execution is disabled. Never present it as investment advice and never claim any returns: the page quotes no return figures.
How it works: a discovery scan (unusual volume plus six profiles: momentum, breakout, pullback, quality, growth, speculative) finds candidates. Research then covers price history, technicals (moving averages, RSI, ATR), financial health, accounting quality, valuation, SEC filings and news, market regime and a unified risk layer. A decision engine combines the results, a thesis state compares the new file with the previous one, and a trade plan gives an entry, an invalidation level and two targets. Quote and portfolio gates must pass before a plan is "setup-ready", a monitored setup is rechecked on a schedule, and a paper order exists only after a person confirms it.
Scoring: fixed weights in code: financial health 20%, unified risk quality 20%, valuation 15%, advanced market evidence 15%, accounting quality 12%, event intelligence 10%, macro regime 8%. A module with no data is left out and the remaining weights are renormalised, so missing data stays unknown instead of counting as zero. The score means attractiveness inside Baby's model. It is not a forecast and not a buy rating.
Who decides what: deterministic engines own the math, the decision engine owns the score, trade-plan code owns entry, invalidation and targets, the risk and portfolio gates own blocks, and the person owns the share quantity and the decision to send a paper order (with a confirmation phrase, after the server recomputes eligibility). The Ask Baby copilot only explains. Model authority over scoring, price levels and risk is zero, and model execution authority is none.
Data sources: SEC company facts and filings (primary), price history providers, Yahoo Finance, Alpha Vantage (an independent second check that never replaces SEC figures in the score), Alpaca market data on the IEX feed for execution-grade quotes, Alpaca news, the Alpaca paper account, and SMTP email for alerts.
Product: a React app with Home, Ideas, Stock Research, Trade plan, Portfolio (monitored setups, paper positions and paper orders are kept as separate lists), Alerts, Reports, Ask Baby, Settings and status, and in-app Docs.
Monitoring and alerts: a scheduler on US Eastern time on weekdays (revalidation around 9:35, a scanner refresh every 15 minutes from 9:45 to 15:45, an afternoon scan around 15:30). An alert is sent when a plan moves from waiting to setup-ready, not every time it stays ready.
Reports: three populations kept apart: historical observations, Baby performance (every setup-ready episode, traded or not) and paper trades (starting at a paper fill). A watch record is never counted as a win or a loss.
Safety: startup refuses a live-trading configuration, the settings screen shows live trading and automatic orders as locked, the server recomputes eligibility when a person confirms an order, and a paper order needs a quantity chosen by the person plus a confirmation phrase.
Stack: Python (package investor/), FastAPI (baby_ui_backend/), React and Vite with Recharts, SQLite ledgers and JSON artifacts, the Alpaca paper API, an SEC company-facts client, Yahoo Finance, Alpha Vantage, SMTP, Cloudflare in front of the site and /api, and systemd on the server.
Limits and next steps: paper trading only. A historical track record is claimed only where point-in-time inputs support it, and automatic retuning of weights from a weak backtest is disabled. Next steps he lists: richer point-in-time coverage, tighter sector and correlation data in the portfolio gate, and a clearer audit export for one symbol. He would not add live trading until the paper record and the quote gate had been watched for a long time.
Typical questions: "Does it make money?" It measures paper plans and paper fills and claims no returns; it is not live trading performance. "Why not let the model pick the stocks?" The score is a weighted sum of calculated modules, and the model is used afterwards to explain the result in plain English. "Could it send a real order by accident?" The order route is the paper API, submission needs a quantity and a confirmation phrase, and startup rejects a live-trading configuration.

== PROJECT: Baby Voice Assistant (personal project; one of two separate projects Adhik calls Baby) ==
Page on the site: https://adhikchintalwar.github.io/adhik-portfolio/#/project/baby-voice
Source code link: not listed on the page yet (suggest contacting Adhik if someone asks for it). Both Baby projects live in one repository.
Naming: Adhik has two separate projects called Baby: this voice assistant and the Baby Equity Research platform. If a visitor only says "Baby", mention both briefly and ask which one they mean. The repository folder for the voice assistant is still called Jarvis Voice (its original name) and the wake word model listens for "hey jarvis".
What it is: a local voice assistant for macOS. You say a wake word and speak a task, and Baby routes it to a specialist agent, runs a real tool on the computer and speaks the result. Wake-word detection, speech recognition and computer actions run on the Mac. A cloud model is optional, and it only ever sees text after a local privacy gate. There is no hosted demo because it runs locally on a Mac with a microphone.
Pipeline: one shared microphone stream, an OpenWakeWord wake word (with a confidence threshold and a cooldown), a session that ends on a stop phrase, silence or about a minute, voice-activity detection and SenseVoice (through sherpa-onnx) transcription, a filter that drops filler and junk transcripts, a router, a specialist agent, a JSON tool decision, the tool registry, an executor, a local MCP server, the tool observation, an optional second reasoning step, and a spoken answer with the macOS say command.
Router and agents: obvious commands skip the model and are matched by phrase rules. Anything else goes to a local Qwen 3 30B model served by Ollama. Agents: Desktop (open apps, folders and projects, screenshots, time, battery, disk and CPU, lock the Mac), Browser (Google and YouTube search, video details, open websites), Workspace (current project status, recent files, git branch), Coding (explains and debugs only; it does not edit files or run commands), and a Planner for small multi-step goals (one to three steps). A memory agent slot exists, but long-term memory is thin.
Tool boundary: the model returns JSON with a tool name and a target, never free text for an action. The registry holds metadata only (name, arguments, privacy level, whether confirmation is required) and never hands the model functions, credentials or connections. Only the executor causes side effects, through a local MCP server.
Observe, then answer: for "find me a good Python tutorial", the first tool collects YouTube titles, then a second local reasoning step picks one, speaks the recommendation and opens the link.
Privacy: a local classifier scans text for keys, tokens, emails and similar patterns, then allows, redacts or blocks it before a single gateway sends anything to the cloud model (NVIDIA Nemotron). The cloud model is told it has no computer: it cannot read files, see the desktop or run commands.
Automations: a SQLite-backed scheduler on its own asyncio thread, so reminders and recurring jobs keep running while the wake-word listener stays on the main thread. Triggers, conditions, actions and outputs are separate registries. The built-in actions today are small, such as reminders.
Stack: Python, OpenWakeWord (ONNX), SenseVoice via sherpa-onnx, Ollama with Qwen 3 30B, MCP, asyncio, SQLite, the macOS say command, an event bus and a portal status file.
Honest limits: the wake word can false-trigger (hence the threshold, cooldown and filler filter), the coding agent only advises, long-term memory is not finished, some tool dispatch still uses explicit branches beside the registry, it does not rebuild a whole plan after an arbitrary failure, calendar, email and GitHub actions are on the roadmap but not working, and it does not click arbitrary buttons. Next steps he lists: a tighter wake word, a real memory store, re-planning when a tool fails, and a confirmation step before any tool that writes files or sends messages.
Typical questions: "Why not just use Siri?" Those products own both the audio path and the action path; Baby is a design that keeps both on the machine, with an explicit tool list and a privacy gate before any non-local model. "Is the model in charge?" It only proposes a tool name and a target; the executor checks the registry and performs the call. "Can it write code on disk?" Not yet; the coding agent only advises. "What if the model invents a tool?" The prompts forbid it, the parser expects a known shape, and the executor looks the name up in the registry, so an unknown name does not run.

== PROJECT: Mac Remote (personal project) ==
Page on the site: https://adhikchintalwar.github.io/adhik-portfolio/#/project/mac-remote
Source code link: not listed on the page yet (suggest contacting Adhik if someone asks for it).
What it is: Mac Remote is a personal project Adhik built. It is a remote control for a Mac that runs in Safari on an iPhone, with no app to install. The phone and the Mac stay on the same Wi-Fi. The phone is a trackpad, a keyboard and a media remote. A Python server on the Mac receives the commands over a WebSocket and turns them into real mouse, keyboard and media-key events. There is no hosted demo, because it controls a Mac on the same network by design.
What it is not: it does not stream the Mac's screen to the phone (no video), it does not work over the internet, it is not end-to-end encrypted, and it is not a native iOS app. The client is a web page.
Why: screen sharing and Universal Control are heavy. This sends input only (move the pointer, click and drag, scroll, type, a few keys and shortcuts, volume, mute, play or pause, lock the Mac), so it stays fast and is enough to drive a computer you can already see, such as a TV, a projector or a desktop across the room.
How it is used: run start.command on the Mac (it makes a Python virtual environment if needed, installs the dependencies and starts the server), open the printed address (like http://192.168.1.20:8765) in Safari on the iPhone, and type the pairing token shown in Terminal. The token is saved in a local file (.pairing_token) so it works next time.
Architecture: iPhone Safari (static HTML, CSS and JavaScript) to a FastAPI and Uvicorn server on port 8765 (serves the page and hosts a WebSocket), a pairing-token check, a process_command function, and Quartz CGEvent calls that post input at the HID level so macOS treats it as real hardware input. A separate process draws a cursor overlay. No database, accounts or cloud: the Mac is the whole backend.
From finger to pointer: the page sends relative movement (dx, dy), not a position. Speed sets a gain of about 1.35, 1.7 or 2.1, and smoothing keeps 65 percent of the previous value and blends in 35 percent of the new one. Movement is buffered and sent once per animation frame (usually about 60 times a second). The server reads the current cursor, adds the delta, clamps it to the combined area of all displays and posts a move or drag event. Nothing waits for a screenshot or an acknowledgement.
Gestures: a tap (under 220 ms, moved under 12 px) is a left click; holding a finger for 350 ms (moved under 8 px) starts a drag, which is released if the phone disconnects; two fingers moving vertically scroll (the change divided by 4, direction flipped to match a Mac trackpad); Left Click and Right Click are buttons.
Keyboard and media: typed text is sent as a string and posted as UTF-16 Unicode keyboard events. Special keys and shortcuts (Esc, Tab, Return, Backspace, arrows, copy, paste, select all, undo, lock with Control+Command+Q) use real key codes. Volume, mute and play/pause use auxiliary media-key events (HID media keys). The server also understands more commands than the phone has buttons for (brightness, track skip, Mission Control, Spotlight, app switcher, screenshots, switching displays, sleep, cursor size and color), so a native client could call them.
Cursor overlay: cursor_overlay.py draws a floating colored circle that follows the real cursor 120 times a second. It is a separate process because AppKit's blocking run loop would freeze the FastAPI server. It converts between Quartz coordinates (top-left origin) and AppKit coordinates (bottom-left origin) per display, and handles up to 16 displays.
Discovery: the start script prints the Mac's Wi-Fi IP address. The server also advertises a Bonjour/mDNS service (_macremote._tcp) through Zeroconf for a future native client, but Mobile Safari does not browse Bonjour itself, so the phone page still uses the printed address.
Security, said honestly: a random URL-safe pairing token (secrets.token_urlsafe(12)) is required on the WebSocket and compared in constant time (secrets.compare_digest). A wrong token closes the connection with code 1008. The overlay only starts after a valid connection. macOS needs the Accessibility permission for synthetic input. It does NOT use HTTPS (traffic is ws://, not wss://), the web page itself is not password protected (only the control channel is), the server listens on all interfaces, there is no per-device revoke (delete .pairing_token and restart for a new token), and drag state is one global flag, so it is built for one phone at a time. The threat model is a stranger on the same Wi-Fi, not a nation-state; he would add TLS and a tighter bind address before using it beyond his own network.
Stack: Python, FastAPI, Uvicorn, WebSockets, PyObjC (Quartz and AppKit), Zeroconf, and plain HTML, CSS and JavaScript with no framework.
Honest limits: several server commands have no button in the phone UI, a few functions in server.py are defined twice (play_pause, find_current_display, jump_to_display), debug logging is noisy, there is no automated test suite, one token and one drag flag with no TLS, and Bonjour is advertised while the shipped client still uses a typed IP address. Next steps he lists: buttons for the existing commands, a native client that discovers the Mac with Bonjour, TLS on the socket, and tests for gesture classification and display selection.
Typical questions: "Why not Screen Sharing?" Those mirror the whole desktop; this sends only tiny input messages and never any pixels. "Why a website and not an iOS app?" Safari is already on the phone, so there is nothing to install and no App Store review; a native app would add Bonjour browsing and background use, which is why the server already advertises its service. "Why relative movement?" A small phone trackpad should not be a map of a large monitor; relative movement with speed-based gain is how laptop trackpads work. "Is it safe?" It is designed for a trusted home or office network with a pairing token; it has no TLS, so it should not be used on untrusted networks. "Does it work away from home?" No, only on the same network, by design.
